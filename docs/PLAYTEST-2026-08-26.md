**Resolved 2026-08-27 — all five.** The through-line was that the game answered
the scouting question for you on turn one; the fix is that it now asks it.

- **C1** — `ScoutingState.watchList` is the GM's own list. It starts empty and
  only grows by an explicit act (right-click menu, profile ☆, the search's star,
  or "★ Track him" in the Centre, which is now the same act). It is not a
  bookmark: `tickScouting` gives pinned players the front of every scout's day —
  at full read rate, capped at half his capacity — whatever his brief says, and
  shields their files from decay. Capped at 40, so a pin costs regional coverage.
- **C2** — `scoutBriefing.ts` builds a real department briefing: bandwidth and
  strain, draft-class coverage, the beats you cover, the youth pools nobody is
  watching, the prospects your own scouts rank 8+ spots apart, and what actually
  moved since the last month-start snapshot (`ScoutingState.coverageLog`).
- **C3** — the Players tab is `playerSearch.ts`: the whole database, filtered by
  name / position / age / league / nation / handedness / contract / cap hit /
  production / read quality, sorted on any column. Ability and ceiling are the
  department's read and come back `null` for anyone unscouted — the search cannot
  see through the fog.
- **C4** — `ScoutGlobe.tsx`: an orthographic canvas globe (dot-field landmasses,
  graticule, atmosphere, coverage arcs from your club), lit nodes where you have
  eyes and dashed rings on the blind spots, paired with a clickable beat list that
  spins the world to a country.
- **C5** — the U17 radar is gated on a real read (it used to hand you the next two
  classes sorted by ceiling); your own board shows "no read" instead of a star
  grade for prospects nobody has watched, and states what fraction of the class
  you have filed on; the public board publishes a rank and a projected ROLE, not a
  ceiling grade. Root cause found and fixed: `createInitialScouting` only fogged
  draft-*eligible* amateurs, so every 14–16-year-old in the world started at
  renown knowledge — which is why the radar arrived pre-filled.

## G. DEADLINE DAY — the season's premier event (added after first triage)

The user: *"it shows things but you cant actually take any actions… it should
actually be immersive and help to see trades / make trades / feel like the league
is more alive. if you wait too long the player you want might get snatched up
live as well… make deadline day one of the premier things to look forward to in
the season."*

**Diagnosis:** the Accept / Counter / Pass buttons and the shopped board already
exist on `DeadlineDayScreen`, so "can't take actions" is probably not a dead
control. The real gap is structural — **deadline day is a single day tick**. The
engine advances the whole day at once, so there is no *during*: nothing unfolds,
nobody can be sniped, and the screen is a static snapshot with a Continue button.

**The change:** sub-day time on this day only. A clock advancing in hours, AI
clubs trading with each other between ticks and landing on a live wire, targets
gettable-then-gone if you hesitate, your own negotiations racing the same clock,
and a "sim the rest of the day" fast-forward with a real recap.

Constraints that shape it: the determinism law (an intra-day clock must be part
of the seeded stream, or byte-identical replay breaks — a frozen gate), save
compatibility mid-day (someone WILL save at 2pm on deadline day), and the day
must stay skippable in one action with identical league outcomes.

The tension the user wants — losing a player by waiting — has to read as a
consequence of dithering, not an arbitrary dice roll.
## Section B — resolved 2026-08-27

### B1 (critical) — every TTS event freezes the game

**It was an architecture problem, and it was two problems wearing one coat.**

*Problem one: the freeze.* onnxruntime-web's WASM inference is synchronous on
its calling thread, and Kokoro was loaded straight into the renderer. Every
synthesised chunk hard-blocked the UI for its entire duration. The existing
chunking split one long freeze into several short ones; it never removed any of
them, because the total work on the main thread was unchanged.

Synthesis now runs in a dedicated module worker (`src/renderer/lib/voice.worker.ts`).
The renderer keeps the policy — chunking, queueing, the clip cache, cancellation,
the never-silent fallback — and pays only for copying the returned PCM into an
AudioBuffer. Audio comes back as a transferable `Float32Array`, so no PCM is
copied across the thread boundary.

Measured with `window.hockeyVoiceBench()` (`src/renderer/lib/voiceBench.ts`), which
times a spoken line against a 10 ms watchdog. Same 284-character line, same machine,
same build — the only difference is where synthesis ran:

| | main thread (as shipped) | worker (now) |
|---|---|---|
| main-thread time blocked | **43,876 ms** | **0 ms** |
| longest single freeze | 43,762 ms | 0 ms |
| line duration | 48,482 ms | 31,389 ms |

During the main-thread run the page could not answer a devtools evaluation for
over 30 seconds. During the worker runs it stayed responsive throughout.

*Problem two: the wait.* A worker cannot make the model faster, and it is not
fast. Timed on the worker's own clock, steady-state synthesis on this machine ran
at roughly **0.6× realtime** — about ten seconds of compute for six seconds of
speech. Below 1.0× no amount of pipelining catches up: every line arrives late and
the gap grows across a scene. That is the other half of *"it takes a long time for
it to be said"*, and it is a throughput fact, not a scheduling one.

Three things were done about it:

* **The opening chunk is held shorter than the rest** (60 vs 110 characters).
  Nothing is audible until the first chunk finishes, so its length alone is the
  silence between the click and the first word.
* **Scenes synthesise the next line while the current one plays.** `speakScene`
  previously started thinking about line *n+1* only after line *n* had finished —
  so every turn of a meeting bought a full synthesis of silence. Look-ahead is
  queued *after* the live line's chunks, and the worker serves requests in arrival
  order, so it can never delay what is already playing.
* **The engine measures itself and stands aside when it cannot keep up.** Below
  1.15× realtime the neural voice hands its lines to the system voice, which
  starts in well under a second. The verdict is remembered across sessions;
  Settings → AI Voices says so, offers "use them anyway", and can re-measure.

Verified in the running app: on the line immediately after the verdict was
reached, time-to-first-audio went from **21,808 ms to 164 ms**, with the main
thread blocked 0 ms.

If the worker cannot start on some platform, or `hockey.voice.mainThreadSynth` is
set, synthesis falls back in-process and behaves exactly as the old build did.
That switch is also the A/B control the numbers above were taken with.

### B2 — the voice talks about the player in the third person

`reaction.outcome` is the engine's **narration** ("Lizotte appreciated being
heard, even if nothing was promised."). The inbox used it as the fallback when
the local writer produced nothing, then quoted it *and spoke it* as the player's
own words.

Every cast call site was audited. The phone (`spokenFromScene`) and both meeting
generators already produce real first-person dialogue; the inbox reaction was the
only offender. It now has an authored first-person pool
(`fallbackReactionLine`, `src/engine/story/reactionVoice.ts`) covering all six
resolved directions, seeded on the player so the same man says the same thing
twice and two men do not. The model remains the ceiling, not the floor — and the
player's reply is now shown for everyone, not only GMs running the local writer.

The bug class has now surfaced three times in three places, so it has a detector:
`looksLikeNarration` (`src/engine/story/spokenText.ts`) flags a line attributed to
a named speaker that names that speaker in the third person and never says "I".
`speakAs` and `speakScene` run it over every cast line in development and warn.
It never silences anything — a false positive must not cost the GM a line.

### B3 — the scout meeting spams voices and dumps everything on one screen

The room now advances one item at a time: the host opens over the board, then
each scout raises his item on his own screen, speaks once, and waits for an
answer. `Back` / `Next` move through the agenda, "Item 2 of 3" says where you
are, and "Let the Head of Scouting handle it" still exits at any point. The next
speaker is pre-synthesised while the current one talks, so moving on is instant.

### B5 — the postgame screen is slow and clunky

TTS is not on this path, so B1 did not fix it. Two real causes:

* **Space did nothing.** Enter and Escape were bound; Space — which is "next" in
  the inbox — was not. Reaching a receipt and finding the spacebar dead is what
  made the screen feel like it wanted clicking away from. Space now continues.
* **Continue was below the fold.** The action row used `marginTop: auto` inside a
  scrolling column; a postgame receipt plus the month grid is taller than the
  panel, so the buttons were scrolled out of sight and the only visible way out
  was the backdrop. The row is now sticky to the bottom of that column.

For "slow to load", the advance is now instrumented rather than guessed at:
`localStorage.setItem('hockey.perf.advance', 'true')` logs one labelled line per
advance breaking the wall time into the match-day-preview probe, the inbox
snapshot, `continueGame`, and the four view fetches
(`src/renderer/lib/advanceProfile.ts`).

First readings, on offseason days in a freshly generated league:

    [advance] 65ms (no game) — matchDayPreview 1 · inboxBefore 0 · continueGame 35 · views 28
    [advance] 53ms (no game) — matchDayPreview 1 · inboxBefore 0 · continueGame 35 · views 17

So the plumbing around the advance is not the cost: the preview probe is free,
the inbox diff is free, and all four post-advance view fetches together come to
under 30 ms. On a game day the receipt is already built by the sim and returned
O(1), which leaves the full-fidelity game inside `continueGame` as the only
candidate left standing. **A game-day reading has not been captured yet** — it
needs a save in the regular season, which this session could not reach — so that
is the next thing to measure, with the instrument now in place to do it.
